# /design-overview [--check]

## 목적

`/init-project` 가 만든 설계 문서는 루트와 `.specops/memory/` 에 흩어져 있다. 사람이 전체 설계를 한 번에 훑을 수 있도록 **읽기 전용 HTML 한 장**(`.specops/design-overview.html`)으로 묶는다.

구성은 설계서의 통상 순서 — **전체 그림 먼저, 상세는 뒤**:

| 순서 | 장 | 장 머리(그림·요약) | 그 아래 문서 |
|---|---|---|---|
| 머리 | — | 한 줄 설명 · 규모(요구·프로세스·화면·API·문서) · 미결 배너 | — |
| 1 | 개요 | — | 제품 요구 정의(PRD) — 목적·사용자·가치제안·마일스톤 |
| 2 | 시스템 구성 | 계층형 시스템 구성도 | 전체·프론트엔드·백엔드 아키텍처 |
| 3 | 요구사항 | 요구사항 현황(마일스톤 × 우선순위) | 요구사항 |
| 4 | 업무 프로세스 | — | 프로세스 설계 — **프로세스마다 흐름도 바로 아래 정의 표**(그림과 설명을 한자리에서) |
| 5 | 화면 | 화면 현황(목록 + 상태: 미리보기 / 설계 전) | 화면 목록 마스터(화면 흐름도) · 디자인 시스템 |
| 6 | 인터페이스 | API 목록 | IF 설계 · 소비 계약 |
| 7 | 데이터 | ERD | 테이블 설계 |
| 8 | 품질 · 원칙 | — | 테스트 전략 · 헌법 |
| 9 | 추적 · 미결 | 추적표 · 결정이 필요한 항목 | 결정 원장 · 프로젝트 컨텍스트 |

문서가 없는 장은 빠지고 번호가 당겨진다. 목차는 두 단계(장 → 그림·문서)까지만 보여 준다 — 문서 안의 절까지 넣으면 길어져 전체 구조가 안 보인다(찾을 때는 목차 위 걸러 보기). 장 머리로 올린 그림(구성도·ERD)은 본문에서 다시 그리지 않고 안내 + 원문만 남긴다.

그림과 표는 **통상적으로 쓰는 표기**를 따른다:

- **한눈에 보기** — 문서·요구·프로세스·API·화면·미확정·가정 개수
- **시스템 구성도 (계층형)** — 구성 요소를 계층 띠(사용자 → 채널·프레젠테이션 → 애플리케이션 → 데이터·미들웨어)에 놓고 외부 연계는 오른쪽 점선 칸에 둔다. 상자에는 기술(§1 구성 요소 표), 화살표에는 통신 방식(다이어그램 레이블 또는 §2 통신 표)을 적는다
- **요구사항 현황** — 마일스톤 × 우선순위 건수
- **업무 흐름도 (스윔레인)** — 프로세스마다 행위자·화면·서버·데이터 레인에 단계가 번호순으로 흐른다(시작 ● → … → 끝 ◎). 예외는 서버 레인에서 점선으로 갈라진다
- **추적표** — 프로세스 ↔ 요구(FR) ↔ 화면 ↔ API ↔ 테이블. 어느 프로세스에도 연결되지 않은 요구를 따로 알린다
- **API 목록** — 메서드 배지(GET·POST…)·경로·인증·설명. 문서에 남은 예시 블록 행은 뺀다
- **결정이 필요한 항목** — 전 문서의 `<미확정 …>`·`<TODO …>`·`가정:` 을 한 표로
- **화면 현황** — 화면 목록에 상태를 붙인다: `screens/<name>.html` 이 있으면 미리보기 링크, 없으면 `설계 전`. init 직후에는 화면이 아직 설계 전이라 목록이 기준이다
- **문서 본문** — 각 문서 전문. **ERD 는 까마귀발 표기**(엔티티 표에 PK·FK·UK, 관계선 끝에 1·0..1·0..N·1..N), **화면 흐름도**(`stateDiagram`), 우선순위·메서드 배지, 색상 값 옆 견본

## 원칙

- **원본은 계속 마크다운이다.** 이 HTML 은 생성물이고 lifecycle 은 읽지 않는다. 고칠 때는 `.md` 를 고치고 다시 생성한다 — HTML 을 직접 고치지 않는다.
- **LLM 이 쓰지 않는다.** 스크립트가 `.md` 를 그대로 변환한다 — 옮기다 내용이 달라질 일이 없고 토큰도 들지 않는다.
- **외부 리소스 0** — CDN 스크립트·폰트·이미지를 참조하지 않는다. 폐쇄망에서 파일만 열어도 보인다. 의존은 `python3` 표준 라이브러리뿐.
- **기본은 로컬** — 새로 init 한 프로젝트는 `.specops/.gitignore` 가 이 파일을 무시한다. 공유하려면 파일을 직접 전달한다. **설계 문서에 내부 URL·계정 정보가 있으면 그대로 실린다** — 전달 전에 확인한다.

## Process

1. 생성:
   ```bash
   bash "${CLAUDE_PLUGIN_ROOT}"/scripts/design-overview.sh
   ```
   출력 1줄(`DESIGN-OVERVIEW: <경로> (문서 N개 · 지문 …)`)의 경로를 사용자에게 알린다. 설계 문서가 없으면 rc 2 — `/init-project` 를 먼저 안내한다.
2. `--check` — 생성하지 않고 기존 HTML 이 원본과 같은 지문인지만 본다:
   ```bash
   bash "${CLAUDE_PLUGIN_ROOT}"/scripts/design-overview.sh --check
   ```
   `FRESH`(rc 0) · `STALE`/`MISSING`(rc 1 — 다시 생성).

## 한계

- 그림은 문서가 담은 mermaid 의 부분집합(`graph TD|LR`·`erDiagram`·`stateDiagram`)만 그린다. 그 밖의 문법(sequence 등)은 **원문 코드 그대로** 보여 준다 — 틀린 그림을 그리지 않는다.
- 구성 요소의 계층은 **이름으로 추정**한다(예: `API`·`Server` → 애플리케이션, `DB`·`Cache`·`Queue` → 데이터·미들웨어, `외부`·`SMS`·`결제` → 외부 연계). 추정이 틀리면 구성 요소 이름을 역할이 드러나게 고친다.
- 자동 배치라 노드가 많으면 선이 겹칠 수 있다. 그림 아래 "원문(mermaid)" 을 펼치면 원본을 볼 수 있다.
- 채우지 않은 골격(`<프로세스명>` 등)은 프로세스로 세지 않는다. 미확정 목록은 `<미확정 …>`·`<TODO …>`·`가정:` 표기만 모은다(일반 placeholder 판정은 `scan-enrich-placeholders.sh` 소관).
- 낡음은 자동으로 알리지 않는다 — `--check` 로 확인한다. 다만 설계가 끝나는 지점은 스스로 다시 만든다(아래 참조의 호출 지점) — 그 밖에서 `.md` 를 손으로 고쳤으면 이 명령을 다시 실행한다.
