## 1. 한 문장 요약

**LLM 코딩 에이전트가 "다 됐습니다"라고 말할 때, 그 말이 참인지 기계가 확인하게 만드는 플러그인.**

Claude Code 에게 기능을 맡기면 명세 → 계획 → TDD 구현 → 검증 → 리뷰 → PR 까지 자동으로 이어진다. 여기까지는 다른 도구도 한다. specops-ko 의 차이는 **각 단계를 건너뛰지 못하게 막는 강제 장치가 프롬프트 밖에 있다**는 점이다.

---

## 2. 해결하려는 문제

LLM 에이전트에게 개발을 맡길 때 반복되는 3가지 실패가 있다.

### 2-1. 검증하지 않고 완료를 주장한다

에이전트가 "테스트 통과했습니다"라고 말하지만 테스트를 돌리지 않았다. 사람은 그 말을 믿고 커밋한다.

**흔한 대응**: 시스템 프롬프트에 "반드시 테스트를 실행하라"고 쓴다.
**왜 부족한가**: 프롬프트는 요청이다. 모델은 지키기도 하고 안 지키기도 하며, **지켰는지 확인할 방법이 없다**.

### 2-2. 자기가 만든 걸 자기가 심사한다

같은 모델이 코드를 쓰고 리뷰하면 자기평가 편향이 생긴다. "좋아 보입니다"가 나온다.

### 2-3. 세션이 끊기면 맥락이 사라진다

컨텍스트 한계·세션 종료로 진행 상황이 날아간다. 다시 설명해야 하고, 중간 결정의 근거는 유실된다.

## 3. 어떻게 막는가 — 장치 4종

specops-ko 의 설계 원칙은 하나다. **"모델에게 부탁하지 말고, 구조로 막는다."**

### 3-1. 훅 — 프롬프트 밖의 강제

Claude Code 훅은 모델의 컨텍스트가 아니라 **런타임**에서 실행된다. 모델이 무시할 수 없다.

| 훅 | 시점 | 하는 일 |
|---|---|---|
| `SessionStart` | 세션 시작 | 메타 스킬 주입 + 진행 상황 복원 |
| `PreToolUse` | 도구 실행 **직전** | verify 없는 `git commit`·`gh pr create` **차단** |
| `PostToolUse` | 도구 실행 후 | 위반 감사 기록 |
| `Stop` | 세션 종료 | 성공 주장 vs 실제 실행 대조, 자유작업 캡처 |

핵심은 `PreToolUse` 다. **커밋이 일어나기 전에 거부**하므로 사후 경고가 아니라 사전 차단이다.

```
모델: "구현 끝났습니다. 커밋하겠습니다."
  → PreToolUse 훅이 transcript 를 검사
  → 검증 러너 실행 기록 없음
  → deny. git commit 이 실행되지 않는다.
```

### 3-2. 실행-근거 게이트 — 자기보고를 믿지 않는다

여기가 이 프로젝트에서 가장 공들인 부분이다.

**순진한 구현**은 이렇다: 모델이 "verify 했다"고 파일에 쓰면 통과시킨다. 이건 **모델이 자기 면제표를 발급**하는 것이다.

specops-ko 는 대신 **transcript 를 직접 판독**한다 (`hooks/governance-lib.sh:_verify_exec_evidence`):

1. 대화 기록에서 `tool_use`(도구 호출)와 `tool_result`(그 결과)를 `tool_use_id` 로 **join** 한다
2. 호출한 명령이 **실제 검증 러너**인지 앵커 정규식으로 확인한다
3. 그 결과 출력에 `VERIFY: PASS` 가 있는지 본다 (`PARTIAL`·`FAIL` 은 불인정)
4. 그 실행이 **마지막 코드 수정보다 나중**인지 확인한다 (오래된 통과 기록 재사용 차단)

즉 **"돌렸다"가 아니라 "돌린 흔적이 대화 기록에 있다"** 를 요구한다.

이 게이트는 실전에서 여러 번 뚫렸고, 그때마다 막았다. 코드에 남은 흔적이 그 역사다:

| 우회 시도 | 대응 |
|---|---|
| `echo "ran pytest"` — 출력에 토큰만 심기 | 줄 첫 토큰이 러너여야 함(앵커) |
| `cat <<DOC` heredoc 안에 러너 이름 | `<<` 포함 명령 배제 |
| `git commit -m "pytest 로 검증함"` | 매칭 줄 **앞** 줄들을 안전 화이트리스트로 제한 |
| 백그라운드 실행 후 결과 안 보고 커밋 | 스텁 감지 + 발급된 경로의 `Read` 결과까지 확인 |

> **정직한 고백**: 두 번은 잘못 고쳤다. 따옴표 개수를 세는 방식, 인용 상태기계를 흉내내는 방식 — 둘 다 "오산은 안전한 방향"이라고 주석에 적었고 **둘 다 실측으로 반증됐다**. 셸 인용은 정규 파싱이 불가하다는 걸 인정하고, "무엇이 위험한가"를 쫓는 대신 **"무엇만 안전한가"를 허용하는** 화이트리스트로 방향을 뒤집었다. 대가는 미탐(정직한 실행을 못 알아보는 경우)이고, 그건 사용자가 러너를 단독 실행하면 풀린다.

### 3-3. Generator ↔ Evaluator 분리 — 도구 권한으로 강제

구현자와 리뷰어를 **다른 서브에이전트**로 나눈다. 여기서 그치지 않고:

```yaml
# agents/spec-reviewer-ko.md
role: evaluator      # ← 이 마커가 Write/Edit 도구를 박탈한다
```

`validate-structure.sh` 의 `agent_tools` 검사가 이를 잠근다. 리뷰어는 **파일을 고칠 수단 자체가 없어서** 자기가 지적한 걸 몰래 고칠 수 없다.

독립성은 **모델 성능이 아니라 컨텍스트 분리**에서 온다. 실측 근거: 부모 모델(상위 티어)의 self-review 가 놓친 Critical 결함을, **독립된 하위 티어 리뷰어가 잡았다**.

### 3-4. 파일 기반 상태 — 세션에 의존하지 않는다

모든 산출물이 `.specops/<FID>/` 에 남는다. 세션이 끊겨도 파일만 읽으면 이어진다.

```
.specops/20260827-mutation-conf-stale/
├── spec.md · acceptance-criteria.md   무엇을 만들 것인가 (계약)
├── clarifications.md · plan.md         어떻게 만들 것인가
├── tasks.md                            작업 분해 + 의존 그래프(YAML DAG)
├── dispatch/                           서브에이전트 입력 (경로만 전달, 본문 금지)
├── reviews/                            Phase B·C 리뷰 판정 기록
├── evidence.md                         검증 증거 (출력 전문)
├── handoffs/                           단계 간 인수인계 (Decided/Rejected/Risks/Remaining)
└── friction-log.jsonl                  거버넌스 위반 기록
```

서브에이전트에게는 **파일 경로만** 넘긴다. 본문을 프롬프트에 인라인하면 부모 컨텍스트가 오염되기 때문이다.

## 4. Lifecycle 과 멈추는 지점

```
진입 (/start · /maintain · 자연어)
   ↓
analyzing      현재 상태·영향 분석          [유지보수만]  ★ 멈춤
   ↓
specifying     명세 + 수용 기준                          ★ 멈춤 (승인)
   ↓
clarifying     모호성 해소                               ★ 멈춤
   ↓
planning       구현 계획      ← plan-reviewer 가 검토     ★ 멈춤
   ↓
decomposing    태스크 분해 + DAG
   ↓
implementing   태스크별 fresh 구현 → Phase B(스펙) → Phase C(품질)
   ↓
verifying      증거 수집
   ↓
review → security → integration → performance                (표면 없으면 skip)
   ↓
PR 생성                                                   ★ 멈춤
```

**★ 멈춤 = HARD GATE.** 되돌리기 비싼 지점에서만 사람에게 묻는다. 나머지는 자동 통과한다. 스킬·커맨드·에이전트 여러 곳이 HARD GATE 를 선언한다(개수는 §5 의 다른 수치와 달리 여기 적지 않는다 — `grep -rl 'HARD GATE' skills commands agents`).

### chain 이 유지되는 방식 — 3중 SoT 잠금

"다음 단계로 간다"는 정보가 **세 곳**에 있다:

1. `hooks/chain.yaml` — 단일 Source of Truth (11개 edge)
2. 각 `SKILL.md` 의 `## 다음 skill` 섹션
3. 메타 스킬의 chain 목록

세 곳이 어긋나면 `validate-structure.sh` 의 `chain_consistency` 가 **FAIL** 한다. 문서와 동작이 따로 노는 걸 기계가 막는다.

## 6. 무엇을 보장하지 **않는가** — 한계

도입 판단에 이 절이 가장 중요하다.

### 6-1. 의도 위조는 막지 못한다

실행-근거 게이트는 **어휘적 위장**(문자열·주석·heredoc)을 막는다. 그러나:

```bash
export PATH=/tmp/fake    # 가짜 러너를 심고
bash scripts/tests/run-all.sh   # 진짜처럼 실행
```

이건 통과한다. **설계상 수용된 범위**다. 이 도구는 실수와 태만을 막지, 작정한 우회를 막지 않는다.

같은 범위에 드는 것 — 커밋·PR 명령을 **다른 명령의 인자나 이름 뒤에 숨기는** 표기는 인식하지 않는다:

| 인식한다 (정직한 사용에서 나오는 표기) | 인식하지 않는다 (감싸거나 이름을 바꾼 표기) |
|---|---|
| `git commit` · `/usr/bin/git commit` · `\git commit` | `bash -c "git commit …"` · `sh -c` · `eval "…"` |
| `FOO=1 git commit` · `time`/`nice`/`sudo`/`env`(옵션 포함 — `time -p`·`sudo -E`·`sudo -u u`·`env -i`·`env -u X` · 경로로 부른 `/usr/bin/env`)·`exec`/`nohup`/`timeout [-k 5] N` 뒤 | `xargs git commit` · `find … -exec git commit` |
| `if …; then git commit` · `for …; do git commit` · `! git commit` · `case` 가지(`x) git commit`) | `alias gc="git commit"; gc` · `g=git; $g commit` |
| 줄 연속(`git \` + 개행 + `commit`) · `git -C dir commit` · `git -ckey=val commit` | `"git" commit` · `git "commit"` (명령어 자체를 인용) |
| `gh pr create` · `gh pr -R o/r create` · `gh -R o/r pr create` | `gh api repos/…/pulls -f …` (API 로 직접 PR 생성) |

오른쪽은 정규식으로 닫으려 하면 끝이 없고(`perl -e`·`python -c`·…) 정직한 흐름에서 나올 이유가 없는 형태다. 왼쪽도 목록이 전부다 — `command -p`·`exec -a name` 같은 `command`·`exec`·`nohup`·`builtin` 의 옵션 형태는 넣지 않았다(실기록 0건). 줄 연속은 이은 문자열과 **잇기 전 원문을 둘 다** 본다: 주석 줄 끝의 `\` 나 `\\` 는 줄을 잇지 않아 다음 줄이 실제로 실행되는데, 이은 것만 보면 그 커밋을 놓친다. 그 대가로 인자 연속 줄이 `git commit` 글자로 시작하면(`echo a \` + 개행 + `git commit …`) 커밋이 아닌데도 걸린다 — 종전과 같은 동작이다. 그리고 R-1 이 보는 것은 **커밋**이다 — `git merge`·`cherry-pick`·`revert`·`am`·`rebase` 로 생기는 커밋과 `git push` 는 대상이 아니다.

**검증 뒤 변경(`STALE`)의 경계.** 판정 상태가 `STALE` 이면 R-1 은 열리지 않는다. 막지 않는 경우가 둘 있다 — ① 전체 스위트(`run-all.sh`)가 **지금 이 트리**에서 통과했다(통과 마커의 지문이 현재 비문서 트리와 같다 — `run-all.sh` 는 판정 상태를 갱신하지 않는 정식 러너다), ② 달라진 것이 **추적하지 않는 파일뿐**이다(로그·캐시·`.DS_Store` 가 생기거나 바뀐 것 — 커밋에 실리지 않는다. 판정 기록에 남긴 추적 파일 지문 `tracked_nondoc_hash` 와 지금을 대조한다 — 그 필드가 없는 예전 기록에는 적용되지 않고, 다시 검증하면 생긴다. **커밋만 실행하는 명령**(`git commit [-a] -m …` 한 줄 — 앞에 `cd`·변수 줄은 허용)일 때만 적용한다: 훅이 보는 것은 실행 전의 인덱스라, 같은 명령이 커밋 전에 다른 일을 하면 그 사이 인덱스가 바뀔 수 있다. 무엇이 안전한지 명령 글자로 가려내지 않는다 — `&&`·`;`·파이프·명령 치환·경로 인자가 있으면 조회용 명령과 함께여도 적용하지 않는다). 둘 다 `STALE` 차단만 건너뛸 뿐이고 실행 증거·앵커는 그대로 요구된다. 남는 한계: 첫 커밋 전(unborn HEAD)의 저장소는 지문이 퇴행값이라 `STALE` 이 되지 않는다(새 저장소의 첫 커밋을 막지 않으려는 종전 설계 — 그 구간의 셸 수정은 보이지 않는다). 판정 상태 기록이 없는 FID(진행 기록 앵커만 쓰는 흐름)도 종전대로다. FID 구속은 명령 **글자**를 본다 — 한 명령에 다른 FID 를 적은 `run-verification.sh` 글자가 함께 있으면(설명용 `echo` 포함) 그 실행은 증거로 치지 않는다(막는 쪽으로 틀린다).

**worktree 에서 도는 셸의 판정 대상.** 판정 기준점은 둘이다 — git 상태(staged·HEAD·base)는 훅 입력 `cwd` 가 속한 **같은 저장소의 작업 트리**, `.specops`·관할은 **프로젝트 폴더**(메인 worktree). 훅은 이를 위해 `GIT_DIR`·`GIT_WORK_TREE` 같은 환경변수를 정하지만 **훅 프로세스 안에서만** 산다(셸·사용자 환경은 바뀌지 않는다). 한계: 명령이 스스로 git 대상을 옮기면(`cd <wt> && git commit`) 대상을 추정하지 않고 종전 판정으로 둔다. 명령이 다른 작업 트리로 옮겨 커밋하면 문서 면제를 주지 않는다(`_gov_cmd_moves_elsewhere` — 같은 작업 트리면 유지 · 확인 불가는 비면제)(`_gov_git_target`·`_gov_cmd_moves_git`·`_gov_apply_git_target`·`_gov_target_note`).

### 6-2. 기록의 진실성은 검사하지 못한다

리뷰 기록이 **존재하는지**는 기계가 대조한다(`check-review-audit.sh`). 그러나 그 기록의 **내용이 참인지**는 자기보고라 파일 대조로 잡을 수 없다.

### 6-3. 토큰 비용이 든다

단계마다 서브에이전트를 띄우므로 "그냥 시키기"보다 비싸다. 완화 장치가 있다:

- `review_mode: end-loaded` (기본) — 리뷰를 FID 단위 2회로 통합. 리뷰 비용 O(N) → **O(1)**
- `/start-lite`·`/maintain-lite` — clarify·plan 생략 (검증·리뷰는 유지)
- 서브에이전트에 파일 **경로만** 전달 — 계약 밖 첨부 1건당 5~11k 토큰(8~14%) 절감 실측

### 6-4. 큰 기능 1건보다 작은 기능 여러 건이 유리하다

실측: 3-태스크 FID 는 완주했고, 10-태스크 FID 는 **24시간 이상 정체**했다. 태스크 각각은 정상이었으나 FID 전체가 7.5시간 마라톤이 되어 세션 경계에서 이탈했다. 권장 스코프는 **태스크 6개 이하**다. 7~9개면 `FID-SIZE` 경고와 함께 tasks.md 에 분할 계획 1행을 기재해야 하고, 10개 이상이면 대화형에서 FID 분할 없이 구현에 진입할 수 없다(`§auto`·`/start-all` batch 는 분할을 물을 사용자 채널이 없어 차단 대신 분할 계획행과 경고를 남기고 진행한다 · `foundation` 은 층별 FID 로 나눈다 — `decomposing-ko` `## FID 크기 규약`).

### 6-5. repo 밖 산출물에는 맞지 않는다

PPT·엑셀·기획서처럼 **테스트할 코드가 없는** 작업은 chain 이 공회전한다. 메타 스킬이 이런 요청을 감지해 진입을 보류한다 — 실측: PPT 12장·요구사항 133건 작업이 명세 단계에서 사망했고, 한 건은 사용자가 도구 밖으로 이탈했다.

### 6-6. Claude Code 전용

훅·스킬·서브에이전트 모두 Claude Code 런타임에 의존한다. 다른 에이전트로 이식할 수 없다.

## 7. 이 프로젝트의 성격 — 실패에서 자란 코드

이 저장소의 특징은 **자기 실패를 지우지 않는다**는 점이다.

훅 코드(§5 표)의 상당 부분이 주석이며, 그 주석은 "이 코드가 무엇을 하는가"가 아니라 **"이렇게 하지 않으면 이렇게 뚫린다"**를 적고 있다. `docs/case-studies/` 에는 dogfood 마찰 분석 3건이 남아 있다.

실제 사례:

- 커밋 하나가 전체 테스트 없이 나가 main 이 하루 red → 도구 무관 git hook 게이트 신설
- 존재하지 않는 에이전트를 문서가 서술해도 전 테스트가 통과 → `xref_resolve` 검사 신설
- 리뷰 리포트만 남기고 기록을 누락해 감사 추적이 빈 채 통과 → `check-review-audit.sh` 신설
- mutation 예외 목록이 줄 번호로 고정돼 파일이 자라자 **무음으로 부패**(64%→50%) → 역방향 정합 검사 신설

마지막 항목은 이 문서를 쓰기 직전(2026-08-27)에 고친 것이다. 게이트가 잡는 값이 위치 키라면, **그 키의 정합을 확인하는 반대 방향 검사를 쌍으로 둬야 한다** — 한 방향만 있으면 설정 부패가 조용히 통과한다.

## 8. 도입 판단 기준

### 맞는 경우

- LLM 에이전트에게 **실제 프로덕션 코드**를 맡기려 한다
- "다 됐습니다"를 믿고 머지했다가 데인 적이 있다
- 요구사항·테스트·검증이 사람마다·작업마다 들쭉날쭉하다
- 한국어로 명세·리뷰가 오가야 한다
- 유지보수 작업에서 **영향 분석과 회귀 테스트가 자주 생략**된다

### 맞지 않는 경우

- 일회성 프로토타입·PoC — 게이트가 순수한 마찰이다
- 테스트할 코드가 없는 산출물(문서·발표자료·데이터 분석)
- 토큰 예산이 빡빡하다
- Claude Code 를 쓰지 않는다

### 부분 도입

전부 아니면 전무가 아니다. `/start-lite` 로 ceremony 를 줄이거나, 유지보수(`/maintain`)에만 적용해도 된다 — 영향 분석과 회귀 AC 강제는 유지보수에서 가장 값이 크다.
